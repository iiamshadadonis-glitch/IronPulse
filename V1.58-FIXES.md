# DropBeat V1.58

This complete project extends the supplied V1.57 archive. It retains the existing theme, payment and subscription processing, website content, Layout editor, Button Dictionary, database bindings, integrations and previous responsive fixes.

## Persistent PWA sessions and routing

- Admin password login, the existing shared Google/OTP Admin-session creator, and Student/Coach session creation use 300-day persistent `HttpOnly`, `Secure`, `SameSite=Lax` cookies with matching server expiry. Explicit short portal sessions retain their shorter duration.
- Existing valid local sessions are extended only when fewer than 270 days remain. Normal visits do not rewrite the session expiry every time. Expired, revoked or rejected accounts are never revived. Session checks compare parsed SQLite dates, so an ISO timestamp that expired earlier today cannot be accepted because of its text separator. Malformed expiry values are rejected.
- The root route checks the real server-side session before redirecting to `/admin/`, `/student-dashboard` or `/coach-dashboard`. Anonymous root requests do not query D1 for a session. Cloudflare Access identities remain under the existing Access authentication rules.
- Remembered navigation contains only validated, same-origin dashboard paths and harmless view keys. It is keyed by verified role and account ID; authentication tokens, form values and destructive actions are not saved in web storage. Admin Brand Settings, Pages workspaces and Notifications role/category, Student Settings/Memberships tabs and Coach dashboard views can resume.
- Logout clears remembered navigation; a transient authentication outage preserves the last good hint. Existing Home links intentionally open `/?website=1`, so signed-in users can still visit the public site.

## Notifications management

`Settings -> Brand Settings -> Notifications` is registered in both existing Brand Settings routers. Mobile uses the shared segmented control and disclosure icon, category rows, a two-step Settings/Review wizard and the established full-height overlay structure. Desktop uses horizontal role tabs with horizontal category tabs below them.

| Role | Categories and events |
| --- | --- |
| Admin | Financial Notifications: successful payment/subscription, failed payment, cancellation and refund update. Social Media: new comment and message. Support Tickets: new ticket. |
| Student | Financial Notifications: successful payment/subscription, failed payment, cancellation and refund update. Classes & Schedule: class change, session started and studio holiday. Account & Support: approval, account status and ticket reply. |
| Coach | Classes & Schedule: class change, session started, coach leave, schedule request and studio holiday. Account & Support: approval, account status and ticket reply. |

All automatic event rules default to enabled, but a device receives no push until its signed-in user explicitly enables push and grants browser permission. Reset restores the routing defaults without silently granting device permission. The module controls push; existing email, Telegram, WhatsApp, payment and portal-notification behavior remains authoritative.

Every Save and Reset requires the exact lowercase text `confirm`, enforced by the API as well as the UI. Mobile confirmation is a bottom sheet; desktop confirmation is centered. Saves use revision comparison so another window's newer changes cannot be overwritten silently. Review screens are read-only.

Each Send Now action opens a message/review flow, shows the selected role audience and requires a separate exact confirmation. An idempotency key prevents an identical confirmed request from creating duplicate jobs. Manual broadcasts deliberately work independently of the automatic event switch. Progress reports acceptance by push services, not proof that an OS displayed an alert.

## Delivery and synchronization

- Native Web Crypto implements standards-based Web Push encryption (RFC 8291) and VAPID authentication (RFC 8292). The private signing key stays server-side; there is no new frontend dependency or external messaging provider account.
- Dedicated subscription, job and delivery tables form a durable queue. Indexed, cursor-based batches, four concurrent sends, timeouts, limited retries and expiring job leases bound processing. Expired push endpoints are disabled. Recipient eligibility is checked against the current active account and unexpired signed-in session before sending.
- Additive bridges queue push updates after existing receipt/recovery/refund writes, subscription cancellation notices, recent social poll results, support-ticket creation and existing portal notifications. Historical receipt backfills do not broadcast old successful payments. Push enqueue errors do not change those business operations' results.
- Automatic routing rules are read fresh when enqueuing and dispatching. The service worker verifies the current account and rules again before showing a private alert. Disabled automatic events already waiting in the queue are suppressed. Logout, another account or an unavailable policy check cannot expose the previous user's message.
- Save updates the Admin's current cache and broadcasts the revision to same-origin tabs. Returning to Notifications refreshes clean state while preserving unsaved drafts. Private rules, credentials and notification endpoints are not added to public SWR/Edge caches. Notification writes do not invalidate unrelated public catalog data.
- Normal business events and authenticated automation traffic wake the queue. An existing scheduler can also POST to `/api/automation/notifications` once per minute with its existing automation bearer key for unattended retries, future jobs and larger audiences. No scheduler or production push was invoked during verification.
- Notification clicks keep same-origin dashboard routing and retain the legacy Social Inbox/Comments click behavior for older notifications.

## Scope

The release changes 49 original paths for authentication, additive event hooks, router registration, entry points/cache versions and release checks. The other 1,633 original files match V1.57 byte for byte. New files contain the session/notification modules, APIs, tests, notes and verification evidence. The dependency lockfile, original migrations, deployment binding configuration and theme definitions remain unchanged.

Verification uses actual endpoint handlers, SQLite, cryptographic test vectors and browser workflows with synthetic accounts and mocked external services. No production database, payment gateway, OAuth account or real user's push device was exercised. See `V1.58-VERIFICATION.md` for the exact executed coverage.
